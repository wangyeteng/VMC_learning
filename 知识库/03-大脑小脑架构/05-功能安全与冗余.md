# 功能安全 (ISO 26262) 与VMC冗余设计

## 1. 一句话定义
> 功能安全（Functional Safety）确保VMC系统在发生故障时**不会造成不合理的人身风险**。对VMC而言，这意味着即使传感器、控制器或执行器发生故障，车辆也必须保持在可控状态或安全地停下来。

## 2. 核心概念与公式

### 2.1 ASIL等级与VMC

```
ASIL (Automotive Safety Integrity Level):
  QM  → A → B → C → D (D最高)
  
VMC相关功能的典型ASIL分配:
  ASIL D: 横摆稳定性控制 (防止翻车/失控)
         扭矩安全关断 (防止非预期加速)
         制动助力失效补偿
  ASIL C: 扭矩矢量控制 (TV)
         直接横摆力矩控制 (DYC)
  ASIL B: 驾驶模式切换
         参考模型生成
  ASIL A/QM: 能量优化扭矩分配
             舒适性相关的悬架调节

为什么VMC的关键功能是ASIL C/D?
  → 如果VMC错误地输出扭矩 → 可能导致车辆失控
  → 如果VMC在需要时没有介入 → 车辆在极限工况失稳
  → 危害等级: S3 (严重伤害/致命) + E4 (高概率暴露) + C3 (难以控制)
  → ASIL D
```

### 2.2 VMC的安全目标

```
安全目标 (Safety Goals) 是功能安全的顶层要求:

SG1 [ASIL D]: 防止非预期的横摆力矩
  → VMC不能在没有驾驶员/大脑指令的情况下产生横摆力矩
  → 安全状态: 左右扭矩差 = 0 (对称扭矩)
  → 容错时间: <50ms

SG2 [ASIL D]: 防止非预期的纵向加速/减速
  → VMC的总驱动力矩不能超出驾驶员/大脑指令范围
  → 安全状态: 零扭矩或驾驶员踏板映射的扭矩
  → 容错时间: <50ms

SG3 [ASIL C]: 确保稳定性控制在需要时可靠介入
  → 当检测到失稳风险时, VMC必须在规定时间内介入
  → 安全状态: 及时的横摆力矩干预
  → 容错时间: <100ms

SG4 [ASIL C]: 防止单点故障导致完全丧失控制
  → 任何一个传感器/执行器故障不能使VMC完全失效
  → 安全状态: 降级但仍可控
  → 容错时间: <30ms (执行器), <10ms (传感器)
```

### 2.3 VMC的硬件冗余架构

```
推荐的VMC硬件冗余方案:

┌─────────────────────────────────────────┐
│              传感器层                    │
│  ┌──────────┐  ┌──────────┐            │
│  │ IMU #1   │  │ IMU #2   │ ← 冗余IMU  │
│  │ (主MCU旁)│  │ (独立)   │            │
│  └────┬─────┘  └────┬─────┘            │
│       └──────┬──────┘                   │
│              ↓                          │
│  ┌──────────────────────────────┐      │
│  │         主VMC MCU            │      │
│  │   (ASIL D 功能)              │      │
│  │   - 核心VMC算法              │      │
│  │   - 状态估计                 │      │
│  │   - 扭矩分配                 │      │
│  └──────────────┬───────────────┘      │
│                 │                       │
│  ┌──────────────┴───────────────┐      │
│  │        安全MCU (可选)        │      │
│  │   (ASIL D 监控)              │      │
│  │   - 监控主MCU输出合理性       │      │
│  │   - 独立的安全关断路径        │      │
│  │   - 降级模式执行             │      │
│  └──────────────────────────────┘      │
│                                        │
│          执行器层                       │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐         │
│  │MCU1│ │MCU2│ │MCU3│ │ESP │         │
│  │前轴│ │后左│ │后右│ │制动│         │
│  └────┘ └────┘ └────┘ └────┘         │
└─────────────────────────────────────────┘

关键冗余:
  ✓ 双IMU (信号对比 → 检测故障)
  ✓ 轮速传感器 ×4 (一个失效不影响)
  ✓ ESP独立于VMC (最终的安全网)
  ✓ 三电机互为冗余
  ⚠ 方向盘转角传感器 (通常单传感器 → 需要故障检测)
  ⚠ VMC主MCU (单点故障 → 需要安全MCU或ESP兜底)
```

### 2.4 VMC软件的安全分区

```
VMC软件架构应按ASIL等级分区:

┌──────────────────────────────────┐
│         QM 区 (非安全)            │
│   - 驾驶模式管理                  │
│   - 能量优化 (Pareto最优)         │
│   - 日志/诊断 (非安全相关)        │
│   - OTA升级管理                   │
├──────────────────────────────────┤
│       ASIL B 区                   │
│   - 参考模型 (r_ref生成)          │
│   - 驾驶模式参数存储/切换         │
├──────────────────────────────────┤
│      ASIL C/D 区                  │
│   - 稳定性监控与干预              │
│   - 扭矩安全限幅                  │
│   - 故障检测与降级                │
│   - 安全扭矩指令生成              │
│   - E2E通信保护 (端到端)          │
└──────────────────────────────────┘

ASIL分区的实现方式:
  方式1: 同一MCU, MPU (Memory Protection Unit)隔离
    → 成本低, 但需要充分验证Freedom from Interference
  
  方式2: 主MCU(QM/B) + 独立安全MCU(C/D)
    → 安全性最好, 但成本高, 通信复杂
  
  推荐: 阶段1用方式1 (快速验证), 量产后迁移到方式2
```

### 2.5 VMC开发中的安全活动

```
概念阶段:
  □ HARA (Hazard Analysis & Risk Assessment)
    → 识别VMC相关的所有危害场景
  □ 安全目标定义 (Safety Goals)
  □ 功能安全概念 (FSC)

系统阶段:
  □ 技术安全概念 (TSC)
  □ 安全架构设计 (冗余分析, FTA/FMEA)
  □ 硬件安全需求 (HSR) — 双IMU, 独立关断路径等
  □ 软件安全需求 (SSR)

硬件阶段:
  □ FMEDA (Failure Modes Effects & Diagnostic Analysis)
  □ 单点故障度量 (SPFM) ≥ 99% (ASIL D)
  □ 潜在故障度量 (LFM) ≥ 90% (ASIL D)

软件阶段:
  □ 安全软件架构 (ASIL分区)
  □ 软件单元测试 + 集成测试
  □ 软件安全分析 (Freedom from Interference)

验证与确认:
  □ 故障注入测试 (FIT) — 在HIL/SIL/VIL上进行
  □ 实车安全验证 (在封闭场地)
  □ 安全案例 (Safety Case) 汇编
```

## 3. 我的理解

1. **功能安全不是"让车不出故障"，而是"出了故障后车仍然安全"**。VMC需要有优雅的降级路径。

2. **ESP是VMC最好的朋友**：即使VMC全面自研，ESP（来自博世或自研）仍然是最终的安全网。建议保留ESP作为独立的ASIL D安全通道。

3. **安全MCU的必要性取决于架构选择**：
   - 如果ESP独立于VMC → 安全MCU可选项
   - 如果ESP集成进VMC → 安全MCU是必须的
   - 易三方应该保留一个独立的"安全兜底"路径

4. **自研VMC的功能安全认证是最大隐形成本**：ISO 26262认证的时间/金钱成本可能超过算法开发本身。需要提前规划。

## 4. 与易三方平台的关联

- 三电机的冗余性为功能安全提供了更多选择（见单电机失效补偿条目）
- 需要确认: 当前是否有独立的ESP→如果是博世, 它已满足ASIL D
- VMC自研的优先安全功能: 单电机失效补偿 > 扭矩安全限幅 > 稳定性监控
- 功能安全文档（HARA, FSC, TSC）需要尽早启动
